# Web UI 1.0 — ТЗ на переработку

Источник требований: [MASTER_SPEC.md](MASTER_SPEC.md). Полный редизайн обязателен для 1.0, но только после стабилизации API. Ни одна существующая рабочая функция не должна исчезнуть из-за редизайна, кроме явно исключённых из scope. Ниже — проектные решения интерфейса в рамках согласованного ТЗ.

## Навигация и структура
- Dashboard: online/offline/degraded/unknown, счётчики флота, активные задачи, недавние события (до 12h), состояние HUB/Xray/nginx, состояние бэкапов. Не смешивать heartbeat с рабочим LuCI/SSH.
- Routers: поиск, теги, группы, сортировка, фильтры статуса и транспорта, видимый scope, контролируемые массовые операции. Карточка: модель/OS/arch/kernel, RAM/flash/uptime, версия агента и собственного Xray, основной/активный/fallback профили, время последней связи, диагностические статусы SSH и LuCI, сетевые интерфейсы, актуальные LAN-клиенты IP/MAC/hostname/reachability, WoL.
- Transport Manager (Owner): профиль, SNI/domain/port/TLS, используемые устройства, зависимости, masked preview, validate/stage/publish/rollback; назначение профилей, состояние перехода. Disable/delete только если не теряются рабочие подключения; показывать конфликт и блокировку.
- Xray Core Manager: VPS и клиентские версии, источник/дата/проверенная совместимость, check/update/downgrade/restart/rollback по правам; прогресс партий и блокеры.
- VPS Terminal только Owner; Router SSH и удалённый LuCI только по scope. Не ломать Safari, WebSocket, password/askpass и SSH host-key проверки. Терминалы с resize, reconnect indication, понятным закрытием сессии, экранной клавиатурой на телефоне, безопасной обработкой escape/paste; не логировать ввод паролей.
- Backup/Restore: время/цель/шифрование/статус, ручной бэкап, планирование, retention, валидация архива, restore preview и явное подтверждение. Не показывать секреты.
- Updates/Tasks: версия, Stable/Testing, этапы, состояние, причина ошибки, cancel только если безопасно, rollback result, журнал операции. Global Logs/Events/Audit: поиск и фильтры, retention 12h, отсутствие секретов. Users/Settings: Owner/Admin и scopes, optional TOTP, опасные подтверждения, Telegram allowlist/settings, RU/EN, темы, бэкапы и общие параметры.

## Визуальные и UX требования
Единая система компонентов и design tokens (цвета, интервалы, типографика, границы, focus). Нейтральная техническая эстетика, высокая читаемость, без декоративной перегрузки; статус определяется текстом/иконкой, а не только цветом. Светлая, тёмная и system auto; сохранять выбор пользователя. RU основной, EN равнозначный; словари вместо захардкоженных строк, локализовать ошибки и даты, не переводить технические идентификаторы. Desktop — sidebar и рабочая область; tablet — сворачиваемая навигация; mobile — компактные карточки/таблицы с осмысленным горизонтальным scroll, доступные primary actions. Целевые размеры 360, 768, 1280 px и промежуточные. Не допускать обрезанных диалогов/терминалов. Клавиатурная навигация, видимый focus, подписи полей, WCAG AA contrast как инженерная цель.
Показывать loading/empty/error/partial/stale/permission-denied; unknown не является offline. Показывать время последнего успешного обновления; не заменять действительные данные фиктивными. Разрушительные операции: affected targets, consequences, confirmation per Owner policy, серверная проверка, durable transaction progress. Не показывать успех до подтверждения фактической операции. Не сбрасывать введённые данные при ошибке запроса; сохранять draft там, где это безопасно, без хранения секретов в browser storage.

## Реализация и приёмка
Сначала inventory существующих routes/API/UI и матрица parity old→new, зафиксировать текущие скриншоты и проверки. Сохранить backend-контракты или версионировать миграцию. Общий operation API с Telegram; авторизация серверная, скрытие кнопки не является RBAC. Не добавлять framework/тяжёлые зависимости без измерения и обоснования. Разделить реализацию UI на app shell/tokens/i18n, Dashboard/fleet/detail, transport/core, terminal/LuCI/WoL, operations/settings; каждый этап с регрессиями. 
Acceptance: все согласованные модули имеют рабочие действия; Safari/Chrome/Firefox и мобильный viewport; light/dark/system и RU/EN; Owner/Admin scopes и запрещённые прямые API запросы; реальный SSH/LuCI/WoL в согласованном пилоте; нет client-side secrets, ошибок консоли и фиктивных кнопок; потеря связи и ошибка сервера отражаются честно. Существующий UI не удалять до подтверждения parity. Full redesign — release gate, не основание для раннего production deployment.
