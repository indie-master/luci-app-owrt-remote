# Docker Manager и единый Compose

## Транзакции HUB

`status` показывает незавершённую транзакцию. Пока она существует, команды
изменения через Docker Manager блокируются. `recover` работает под общей
блокировкой и сверяет настройки, модель Compose, обнаруженный контейнер,
неизменяемый ID образа и SQLite. Запуск использует ID образа. Для новых
сборок readiness дополнительно сверяет ревизию процесса с меткой образа. Текущая запись хранится в
`/opt/router-orchestrator/.transaction.json` с mode 0600. При начале следующей
операции предыдущая терминальная запись переносится в именной файл журнала.
Незавершённая установка может продолжиться с тем же проверенным образом и
каталогом состояния.

При переключении Manager сохраняет резервную копию после подтверждения
остановки HUB. В случае сбоя до записи решения о commit он запускает исходный
образ только после проверки целостности SQLite и точного совпадения
`sqlite_schema`, `user_version` и `application_id`. При отличии схемы текущая
БД, образ и журнал сохраняются для разбора. Сбой записи истории релиза после
решения о commit возобновляет фиксацию выбранного образа. Явный `rollback`
требует подтверждённых ID обоих образов и совместимой схемы. Записи истории
старого формата остаются читаемыми, но сами по себе не подтверждают
совместимость. Автоматического восстановления старой копии поверх текущей БД
нет. Равенство схемы проверяет структурную совместимость. Изменения
прикладной семантики данных под той же схемой требуют отдельной проверки
кандидата. Для обновления сохраняется `--acknowledge-schema-risk`.

Офлайн-бэкап записывает согласованный SQLite snapshot на диск через SQLite
Backup API. Архив формата 1 создаётся потоком с SHA-256 для каждого файла.
Лимиты создания и чтения составляют 2 ГиБ сжатого архива, 4 ГиБ данных вместе
с manifest, 9 999 файлов состояния и 4 МиБ manifest. Закрытый архив
синхронизируется и атомарно публикуется с синхронизацией каталога. После
аварийного завершения возможны приватные временные каталоги
`.router-backup-*`. Финальные архивы имеют имена
`router-orchestrator-*.tar.gz`. Бэкап блокируется и при работающем host HUB.
`restore` проверяет завершение tar/gzip, хэши и SQLite. Целостность
самодостаточного снимка проверяется в режиме immutable, чтобы SQLite
не создавала служебные WAL/SHM. Manager синхронизирует
проверенные файлы и публикует дерево через Linux `renameat2(RENAME_NOREPLACE)`.
Если процесс убит до публикации, на месте назначения данных нет. В родительском
каталоге может остаться приватный `.router-restore-*` для разбора.

## Три профиля корневого Compose

Для нового стека используется корневой `docker-compose.yml`. Без профиля
он сохраняет прежний режим HUB-only для Docker Manager. Опциональные
сервисы включаются одним из трёх профилей.

| Профиль | Сервисы | Входящий трафик |
| --- | --- | --- |
| `standalone` | HUB, Xray, nginx | Внутренний nginx принимает публичное HTTPS-соединение, выбирает upstream по SNI и направляет домен HUB на свой TLS backend |
| `external-stream` | HUB, Xray, nginx | Внешний nginx передаёт SNI домена HUB на loopback TLS-порт внутреннего nginx |
| `external-only` | HUB, Xray | Внешний nginx завершает HTTPS для HUB и маршрутизирует WSS и HUB к разным loopback-портам |

`RO_STREAM_ROUTES` задаёт адреса Xray в виде списка `dns-name:port` через
запятую. Для REALITY и других TLS passthrough маршрутов используйте отдельные
SNI. Маршрутизация HUB и WSS по пути выполняется после TLS-терминации.
Xray и HUB используют общий loopback хоста, необходимый для существующих
reverse-портов LuCI/SSH. Для стенда обязательны выделенные порты и отдельные
каталоги состояния, Xray, assets и TLS. Внутренний nginx читает
`fullchain.pem` и `privkey.pem` из монтируемого каталога TLS. Для
`external-only` можно выделить пустой TLS-каталог Xray, если его конфигурация
не ссылается на сертификаты.

Для офлайн-подготовки создайте отдельный файл настроек на основе
`.env.example`, укажите свой профиль, тестовые пути и проверенные digests
образов, затем передайте этот же файл генератору и Compose.

```sh
python3 tools/orchestrator_stack_config.py --env-file "$fixture_env" --output-dir "$new_render_dir"
env -i PATH="$PATH" HOME="$HOME" docker compose --file docker-compose.yml --env-file "$fixture_env" \
  --project-name "$fixture_project" --profile "$fixture_mode" config --quiet
```

В `fixture_project` и `fixture_mode` используются выведенные генератором
`project_name` и `profile`. Для профилей с внутренним nginx
`RO_NGINX_CONF` должен указывать на `nginx.conf` в новом каталоге вывода.
Закреплённая сборка nginx для standalone должна иметь модули stream,
ssl_preread и HTTP/2. Для сборки с динамическим stream-модулем укажите
`RO_NGINX_STREAM_MODULE=/usr/lib/nginx/modules/ngx_stream_module.so`.
Внешние фрагменты предназначены для проверки и ручного согласования.
Генератор не обращается к внешнему nginx, сертификатной инфраструктуре
или Docker daemon.

Исторические файлы под `deploy/` и host-adapter overlay сохранены для
совместимости старых сценариев под HOLD. Они не нужны для новых профилей.
Миграция этих сценариев, launch/preflight с реальным Xray и nginx,
проверка всех транспортов и переключение на действующем хосте требуют
отдельной приёмки.
