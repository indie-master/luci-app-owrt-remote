# Router Orchestrator 1.0 — утверждённое ТЗ

Дата согласования: 25.11.2026. Это нормативные требования, не заявление о готовности функций. При расхождении с историческими документами данный документ имеет приоритет в части целевого продукта; существующие меры защиты и production-hold сохраняются. См. также AGENTS.md и отдельное ТЗ Web UI (после добавления).

## 1. Назначение и границы
Публичный самостоятельный control plane для OpenWrt, десятки — сотни устройств на одном HUB. Независим от SwiftlessVPN/Remnawave; общие домены и сосуществование обязательны. Надёжность выше функциональности и размера. Один HUB на VPS; резервный HUB — после 1.0. Никакой внешней телеметрии. Управление пользовательским VPN/трафиком не входит в проект.

## 2. Production policy
Без отдельного согласия: разработка в рабочей ветке, CI, изолированный staging, read-only диагностика Belt. Только после явного согласования конкретного изменения: production hotfix, HUB/агент/Xray upgrade, смена транспорта, внешний nginx, перезагрузка VPS/роутеров, удаление старых сервисов/данных, push main, публикация релиза. Системная сеть и firewall без отдельного согласования запрещены; агент сам их не меняет. Разрешение на разработку не означает разрешение на live apply. Изоляция staging: отдельные state, ports, container names, locks и credentials; никакого общего writable production state. Preserve HOLD, rollback images, active worktree и действующие каналы. Не трогать Movietonn до проверенного стабильного обновления; main и Netis N6 — пилоты только после согласования; прочие устройства аналогично.

## 3. Архитектура и установка
Debian/Ubuntu amd64 в первую очередь; один Compose entrypoint, отдельные HUB, Xray, опциональный nginx; SQLite, без Redis/PostgreSQL. Три режима: standalone, external proxy + internal nginx, external proxy only. Stream/SNI ingress, 443 в приоритете, гибкие домены/поддомены/порты; HTTP path routing только после TLS termination, REALITY passthrough. Валидировать конфликты, не обещать различение идентичного SNI без механизма демультиплексирования. Генерировать внешнюю конфигурацию без автоматической правки чужих сервисов. Managed TLS (LE), external certs, external TLS termination. На Belt существующий независимый ssl-renewal с Cloudflare DNS challenge не изменять; не вмешиваться в Certbot, сертификаты, таймеры, другие сервисы. Поддержать обновление внешних сертификатов без их присвоения проектом.
Интерактивный и noninteractive .env install: preflight OS/resources/Docker/ports, mode/domain/TLS/admin/transports, generation, validation/start, connection details. CLI Install/Update/Repair/Edit/Backup/Restore/Rollback/Uninstall; Update через UI и CLI; Stable/Testing. Обнаружить старый systemd и предложить миграцию; при отказе остановиться. Резервировать и проверять обратимость.

## 4. Transport Manager
WSS/TLS основной, REALITY TCP, XHTTP/TLS, gRPC/TLS дополнительные, создаёт Owner по необходимости. Глобальные профили, несколько экземпляров одного типа, индивидуальное назначение основного и ordered fallbacks. Один активный управляющий транспорт, временный параллельный probe допустим. Индивидуальные credentials. Owner CRUD/validate/stage/activate/disable/delete, блокировать удаление используемого профиля без безопасной миграции. Нет raw JSON editor. Серверный и клиентский render, проверка целевых бинарников, функциональные heartbeat/LuCI/SSH, транзакционное promote, независимый rollback. TCP Legacy не предлагать при clean install; сохранить действующих клиентов до подтверждённой миграции всех, затем согласованный вывод из эксплуатации. Никаких новых незашифрованных подключений.
Fallback per-router on/off, порядок настраиваем; defaults: loss 60s, critical latency 1500ms, failed checks 50%, stable primary 180s, cooldown 120s, heartbeat 30s. Не переключаться на худший резерв по причине latency; исключить flapping, cooldown не блокирует аварийный recovery. Все пороги настраиваемые; автономный локальный recovery при отсутствии всех профилей без reboot и правок сети. Auto return только на активный и проверенный primary. Локальный last-known-good. Проверка после reboot обязательна при приёмке, reboot только с согласия. Уведомления о потере/возврате/переключении и важных ошибках.

## 5. Core и OpenWrt
Собственный Xray на VPS и роутере: изолированные binary/config/PID/service/storage; не трогать Podkop/Forkop/Tachyon/system Xray/Remnawave. Только official releases, проверенные матрицей server/client/core/arch/transport; проверка checksum и config обязательна, fail closed. Авто проверка наличия релизов без auto install. VPS start/stop/restart/select version/upgrade/downgrade/automatic rollback. Клиентская версия видна в HUB, индивидуальное и небольшими группами обновление по подтверждению, остановка при ошибке и rollback. Не считать syntax test совместимостью.
OpenWrt >=23.05 (24.10 и выше); все архитектуры с официальным совместимым Xray и пройденными тестами. Shell installer по ссылке из репозитория приоритетен, IPK/APK, обязательный LuCI. Динамический preflight свободной RAM/flash, включая Xray и rollback. Бюджет самого агента без Xray/системных зависимостей: RAM <=15 MB, flash <=5 MB, heartbeat 30s. Специальную установку на extroot/USB не реализовывать. Inventory model/arch/kernel/firmware/resources/packages. Update через HUB, CLI, локальный LuCI. Uninstall удаляет только собственные компоненты и восстанавливает только собственные изменения, не чужие поздние настройки. Не изменять firewall/DNS/DHCP/Wi-Fi/routes/system Xray.

## 6. Web UI и доступ
Обязательные модули: Dashboard, fleet list, router detail, Transport Manager, Core Manager, VPS Terminal, Router SSH Terminal, remote LuCI, WoL, текущий LAN list IP/MAC/hostname/reachability, network/interface monitoring, Global Logs, Backup/Restore, Update Manager, Task Manager, events/alerts, admin audit, users/permissions, global settings. Groups/tags/search/filter/bulk permitted actions. Полная переработка дизайна в 1.0 без регрессий; mobile/tablet, RU/EN, light/dark/system. Единый API/операционная логика Web/Telegram. Исключены: сервисы OpenWrt как отдельный менеджер, packages, files, config history, third-party integrations, массовые shell команды, firmware upgrades, LAN traffic history, blocking/shaping и изменение сети.
Роли только Owner и Admin; Admin ограничен назначенными роутерами/группами. Owner-only server transports, server Core/HUB lifecycle, VPS root terminal, global security/users/backups/restore. Local login/password, optional TOTP для всех, OIDC после 1.0. Подтверждение опасных действий настраивает Owner; server-side RBAC всегда, включая API/terminal sessions. Регистрация: предварительная запись в HUB и персональная команда; не требуются публичные одноразовые ссылки/коды. Проверить текущую привязку UUID к agent identity; не допускать impersonation. Транзакционная ротация UUID/credentials без reinstall; немедленный отзыв доступа включая активное соединение. Секреты не выводить в logs/UI/API без необходимости.

## 7. Telegram
Встроенный опциональный компонент, без него HUB полноценен; отдельный allowlist Telegram admin IDs, явные permissions/scopes, индивидуальные подписки на события и группы; общая серверная логика проверок прав. HTTP proxy, anti-spam/dedup, уведомления offline/online/fallback/update failure/resources/overheat/SSH/LuCI. Уведомления обязательны в 1.0, полноценное администрирование позже. Dangerous actions с отдельной кнопкой; shell команды запрещены. Обновление HUB/Xray, смена транспорта, restore только Web/CLI. Не выдавать Telegram доступ по факту знания bot username.

## 8. Backup, restore, logs
Automatic backup каждые 12h, manual, 3 последние копии (настраиваемо), одновременные targets local/Telegram/email/S3/SSH. Внешние копии обязательно зашифрованы, локальные опционально. Сохранять SQLite consistent snapshot, settings, tokens, certs, Xray/nginx configs, Compose; для воспроизводимости manifest версии/дигесты (техническое решение). Restore одной командой на подготовленном VPS, target RTO 30 min, плановый RPO 12h при успешном расписании. Проверить архив и восстановление, ключи шифрования вне архива. Router backup: agent-only и стандартный полный config OpenWrt, backup before change/update. Миграция на другой HUB без физического доступа, с проверкой и откатом. Все журналы, включая аудит и Docker-managed logs, удалять старше 12h; size caps; не путать runtime logs с durable state незавершённой транзакции, необходимым для rollback. Не хранить секреты в логах.

## 9. Roadmap и критерии этапов
1. Audit/stabilize: inventory code/CI/live evidence, reconcile production hotfix Safari/VPS terminal/SSH/WoL/Docker Xray, PaxoBs SSH, DB/Xray parity, migrations. Preserve all functioning channels; distinguish observed/claimed/not-tested.
2. Docker/installer: all three modes, clean install, migration, update/repair/edit/uninstall, no destructive side effects; external TLS compatibility.
3. Security/recovery: Owner/Admin scoped API, optional TOTP, transaction locks, encrypted remote backups and tested restore.
4. Transport Manager: four secure transports validated end-to-end, profile operations, safe migration off Legacy.
5. OpenWrt: clean install/update/uninstall/rollback, LuCI, package formats, resource/arch validation.
6. Fallback: offline/latency/failure thresholds, no flapping, local recovery, reboot persistence, no system network changes.
7. Core: tested official versions only, checksum/config, downgrade, rollout batches and rollback.
8. Web UI: full redesign, parity, mobile, RU/EN, themes, browser/terminal tests.
9. Telegram: mandatory notifications; full administration deferred.
10. Stable release: CI, virtual + physical acceptance, 1–3 day pilot, documentation, explicit release approval.
11. Post-1.0: backup HUB/failover; OIDC and full Telegram admin.
Baseline security/backup/testing apply from stage 1, not only stage 3. Do not mark tasks passed with mocks alone; report scope. Preserve current PR #18/branch until audited. main/dev/feature/fix/release workflow. README.md Russian primary, README.en.md English link, details docs/. Physical dedicated device absent; virtual tests now; physical tests and pilot remain release blockers. All stages 1–10 and listed mandatory features are required for 1.0; no unapproved production operations.

## 10. Implementation defaults and open verification (not new approvals)
Use small batch sizes, measurable check windows, bounded retries, secure credential storage and narrowly scoped privileged adapter; choose exact values by tests and document them. Separate user-controlled deployment settings from project defaults. Current Git and production must be audited before replacing historical runbooks. Any version/architecture not verified remains unsupported/unverified; no invented matrix rows. For stage 1, CI green is not proof of runtime health.
